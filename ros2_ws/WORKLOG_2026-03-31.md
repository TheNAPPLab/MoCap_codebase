# Worklog for 2026-03-31

## Summary

Today's work focused on getting a single-marker physical Crazyflie (`cfB`) to run a figure-8 demo safely under Crazyswarm2 with OptiTrack motion capture.

## What was added

- Added a new `figure8_demo` example node that:
  - loads the existing figure-8 CSV trajectory
  - publishes the planned path as an RViz marker
  - optionally waits for a fresh mocap lock before flight
  - auto-arms the physical drone and waits for the required supervisor bits
  - uses the latest live mocap pose as the flight base pose when available
- Added `figure8_demo_launch.py` to run the demo with the standard Crazyflie stack.
- Added `figure8_logged_launch.py` to run the stack plus rosbag recording for flight-debug sessions.
- Added `figure8_demo.rviz` to visualize TF and the planned figure-8 path.
- Registered the new example in `setup.cfg` and added the required ROS message dependencies in `package.xml`.

## What was changed in the Crazyflie stack

- Updated `crazyflie/launch/launch.py` so RViz gets a cleaned Snap/GTK environment, which avoids RViz startup failures from Snap-based terminals such as VS Code.
- Updated `crazyflie/config/motion_capture.yaml` for the single-marker setup:
  - left `interface_ip` unset for the open-source OptiTrack backend
  - restored the `default_single_marker` marker point and offset that match the single-marker tracker model
- Updated `crazyflie/config/crazyflies.yaml` so `cfB.initial_position` reflects the latest observed live pose instead of the older stale start point.

## Flight-debug work completed today

- Verified NatNet data flow from the OptiTrack machine and checked both rigid-body and unlabeled-marker streaming.
- Confirmed that `cfB` is configured as a single-marker robot using `librigidbodytracker`.
- Diagnosed early figure-8 failures caused by stale absolute start positions being used after takeoff.
- Patched the new demo to use the live mocap pose as the base pose instead of relying only on the saved YAML start position.
- Patched the new demo to arm explicitly before takeoff and wait for the drone to report an armed, flyable state.
- Ran multiple physical hover/figure-8 attempts and captured rosbag/log data for investigation.
- Investigated tracker and server logs during failed takeoffs and found repeated `all dynamic check failed for rigidBody cfB` warnings during bad flights.
- Tested the `optitrack_closed_source` backend as a compatibility fallback and then reverted it because it did not publish usable live `/poses` or `/pointCloud` data on this machine.

## Current state at the end of the day

- The software-side stale-start and auto-arm issues are fixed in the new demo flow.
- The remaining blocker is physical mocap identification, not the ROS flight command path.
- The open-source OptiTrack backend is currently publishing one stable point around `(-0.05756, 0.03170, 0.28627)`, and the tracker is turning that into a stable `cfB` pose around `(-0.03984, 0.03565, 0.30203)`.
- That is not safe for another automatic takeoff if the real drone is expected to be sitting on the floor, because the mocap system appears to be locked onto the wrong physical marker or an incorrectly placed marker.

## Not committed

- Rosbag output under `results/` was left uncommitted because it is generated flight data, not source code.
